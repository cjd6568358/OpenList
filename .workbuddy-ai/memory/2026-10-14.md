## 2026-10-14 00:47 — 在线播放 MP3 失败 = MIME 缺失（真根因）

- 现象：`/d/itvsh/Music/*.mp3?sign=...` 在前端无法在线播放；WMA 同样失败但那是浏览器解码器不支持（Chromium 无 WMA 解码器，Go 版也一样）。
- 真根因（MP3 这种浏览器明明能解的也失败）：`/d/`、`/p/` 的 `Content-Type` 走 `mimeFor()`，固定表里**没有 .mp3** → 回落 `application/octet-stream`。浏览器 `<audio>/<video>` 只接受 `audio/*`、`video/*`，遇到 octet-stream 直接报 "no supported source"。Go 版在 Linux 上 mime.TypeByExtension 会读 /etc/mime.types 拿到 audio/mpeg，所以 Go 能放。
- 修复：`api.zig mimeFor()` 补齐常见音视频 MIME（.mp3→audio/mpeg、.wma→audio/x-ms-wma、.m4a、.mka、.mid、.amr、.ape、.m3u、.avi、.wmv、.asf、.flv、.rmvb、.rm、.3gp、.ogv、.m4v、.mpg/.mpeg），新增回归测试 `mimeFor gives media types the browser audio/video elements accept`。
- 打包机 **342/342** 通过；aarch64 1,158,592 B，sha256 `4e0b4a99b18fbeafe13dd7f0dc1d729f87e73fc79be0b97ad65aa38eb7c083bb`，已部署光猫。
- 真机验证：同一 mp3 链接现在 `Content-Type: audio/mpeg`，Range 206 正常（`bytes 0-99/4661517`）。
- 遗留边界：WMA 仍不能网页播放 —— Chromium 内核没有 WMA 解码器，属浏览器能力限制（Go 版同样），本地播放器/WebDAV 可播。`remote.py` 单引号内 `$(...)`/awk 组合命令在光猫 ash 上不可靠，重启用固定 PID 或分步执行。

## 2026-10-14 00:56 — 播放器 401 = raw_url 缺 sign（第二个缺口）

- 现象：前端音频播放器直接请求 `raw_url`（`/p/...` 无 `?sign=`）→ 401 → `NotSupportedError`。MIME 修好后暴露的第二个缺口。
- 根因：Zig `handleFsGet` 给代理存储生成的 `raw_url = "/p{path}"` 不带签名；前端播放器**原样使用 raw_url**，而 sign_all 部署下无 sign 的 `/p` 必 401。Go 侧对应行为是 `common.GenerateDownProxyURL`（proxy.go:31-33）生成 `/p` URL 时带 `?sign=`。
- 修复：`raw_url = "/p{encodePath(path)}?sign={sign_val}"`（sign_val 与 `sign` 字段同一值，路径用 `urlmod.encode(·, .path)` 对齐 Go `utils.EncodePath(path,true)`）；无 sign（sign_all 关）时仍回不带查询串的形态。
- 打包机 **342/342**；aarch64 `1,159,000 B`，sha256 `3fef0f283461b0cd2440ff084f0e05c757332115968a01ea4b0d43d80b376d54`，已部署（单进程 8941）。
- 真机端到端：`fs/get /itvsh/Music/陶晶莹 - 太委屈.mp3` → `raw_url` 含 `?sign=LETPO3M4g…=:0`；无 token 直接 GET 该 raw_url + `Range: bytes=0-99` → **206 + audio/mpeg**。
