## 2. 编译机验证：当前不是全绿

编译机 `10.0.0.4`，已有工具链 `/root/.cache/zig/zig`，实测版本 `0.17.0`。源码上传到独立目录 `/root/olz-audit-20261011`，全局缓存也放该目录内，不在工具链目录写缓存。

### B01 / P1 / 确认：Linux 测试命令缺少 libc

- `tools/build_remote.py:48` 调用 `zig test src/tests.zig`，没有 `-lc`。
- Linux 路径实例化 `src/drivers/local.zig:341,346-351` 的 `extern "c" statvfs`；Windows 测试不经过该分支。
- 在编译机对原上传目录复跑的真实错误：

```text
src/drivers/local.zig:341:8: error: dependency on libc must be explicitly specified in the build command
extern "c" fn statvfs(path: [*:0]const u8, buf: *Statvfs) c_int;
```

- 建议：Linux 测试统一显式 `-lc`；不能把“Windows 测试通过”推成“Linux 测试命令正确”。

### B02 / P1 / 确认：当前源码新增非法测试文档注释

- `src/drivers/cloud189pc.zig:2175-2179` 把 `///` 文档注释直接挂在 `test` 上；Zig 0.17 不允许。
- 本轮在编译机分别执行测试与交叉编译：

```sh
ZIG_GLOBAL_CACHE_DIR=/root/olz-audit-20261011/global-cache \
  /root/.cache/zig/zig test src/tests.zig -lc
ZIG_GLOBAL_CACHE_DIR=/root/olz-audit-20261011/global-cache \
  /root/.cache/zig/zig build-exe src/main.zig --name openlist \
  -target aarch64-linux-musl -O small -lc -fstrip
```

两条均返回失败，首个诊断一致：

```text
src/drivers/cloud189pc.zig:2175:1: error: documentation comments cannot be attached to tests
```

- 建议：这几行改普通 `//` 后再跑完整测试和交叉编译；首错修掉前不能断言后面没有别的错误。
- **当前没有产生合格新二进制。** 旧 `dist/openlist-aarch64` 不代表当前工作树。

### B03 / P1 / 确认：构建验收脚本会丢失失败状态

- `tools/build_remote.py:48,55-58` 通过 `| tail` 截断编译器输出，未启用 `pipefail`；`rc` 未形成有效的编译失败闸门。
- `:50` 写死检查 `All 212 tests passed`，新增测试后即使通过也会被误判失败。
- `:58-64` 未校验远端二进制确实是当前构建生成，便尝试下载；缺少稳定源码指纹与产物关联。
- 建议：完整保留日志，按进程退出码验收，不固定测试数；test 失败不得 build，build 失败不得 get；产物校验 ELF、静态链接及 SHA-256。

### B04 / P1 / 确认 + 安全风险：远程传输脚本尚不合格

- `tools/remote.py:34,47-59` fallback 用 64 KiB + `base64 -d`，与设备已知“无 base64、32 KiB 原始字节分块传输”约定冲突；并未检查每个 `sh()` 的退出码。
- SFTP 任意异常后直接清掉远端目标再重传，可能破坏已有文件；上传后无完整性确认。
- `tools/remote.py:7,15` 将共享密码放入源码/说明，`connect():21` 自动接受未知主机密钥。报告不复述密码。
- 建议：密码由环境/交互凭据注入；校验已知 host key；上传到新临时文件，校验 hash 后原子安装；不支持 SFTP 时使用原始字节通道而非依赖 base64。

## 3. 本轮补查出的部署与迁移问题

### C01 / P1 / 确认：Local/WebDAV 配置字段并不兼容

- Go `internal/driver/item.go:30-39` 的 RootPath 使用 `root_folder_path`；Local 嵌入 RootPath（`drivers/local/meta.go:8-18`）。
- Zig `src/drivers/local.zig:26-46` 只读 `root_folder`，没有迁移别名。直接喂 Go addition 时忽略原根目录，回落 `/data`，可能启动失败或展示错误目录。
- Go WebDAV `drivers/webdav/meta.go:8-14` 用 `address` 和 `root_folder_path`；Zig `src/drivers/webdav.zig:44-65` 用 `url` 和 `root_path`，且 `:103` 空 URL 直接报 InvalidConfig。
- 建议：兼容旧字段并明确优先级，增加“真实 Go addition JSON → Zig 配置”的测试，而非只测 Zig 自产 JSON round-trip。

### C02 / P1 / 确认：驱动会话回写没有接上实际 storage id

- 主应用 `src/main.zig:158-170` 统一调用 `Factory.create(gpa, &add_val)`，没有传 storage id；`src/driver.zig:170` 工厂签名也不提供 id。
- 云驱动默认工厂给 id=0：例如 `src/drivers/aliyundrive.zig:1306-1308`、`quark.zig:1069-1071`、`115open.zig:1584-1586`、`itvsh.zig:1365-1374`；123/189pc 也是 `createWithId(...,0,...)`。
- 多个 `save()` 以 id=0 直接返回；itvsh 即使调用 persist，也到 `src/main.zig:218` 的 `storageById(0)` 通常查无记录。
- Go `internal/op/storage.go:296-306` 从真实 Storage 取 id 并落库；例如夸克 `drivers/quark_open/util.go:433-434` 刷新后调用保存。
- 后果：token/cookie/forwardUrl 虽能在进程内刷新，重启后不一定保留，刷新令牌轮换后可能彻底失效。
- 建议：工厂上下文携带真实 id，并测“刷新 → 保存 → 重启加载”的主应用链，不只测 createWithId 独立 helper。

### C03 / P1 / 确认：不是复制 Go config.json 即可迁移全部存储

- Go storage 来自数据库：`internal/db/storage.go:GetStorages`、`internal/model/storage.go`；Go `internal/conf/config.go:Config` 并不包含 Zig 使用的存储数组。
- Zig `src/config.zig:273-274,286-305` 只读顶层 `storages` JSON 数组，不读取 Go SQLite。
- 这是放弃数据库的已知设计边界，但旧文档的“Go → Zig 单向安全迁移”表述过宽：仅 scheme 等基础配置兼容，不包含数据库中的 storage、用户、settings。
- 建议：先导出目标九驱动记录，转换字段/驱动键名，生成隔离的 Zig 配置；禁止覆盖现有 Go 配置和数据库。

## 4. 鉴权、API 与数据生命周期

### A01 / P0 / 确认：首次注册把请求内存存进长期配置

- `src/api.zig:335,342-345` 在 request arena 分配用户名/哈希，再传给 `cfg.putZig`。
- `src/config.zig:98-126` 只存 Value 引用，不复制字符串到配置 arena。
- `src/http.zig:450-452` 请求结束释放该 arena；之后设置保存/会话保存会再访问原字符串。
- 后果：悬空引用、重写配置时损坏或访问已释放内存。`app.admin_hash` 的另一次复制不修复 `cfg.root` 的所有权。
- 建议：明确 putZig 的复制契约；用户名、键和所有嵌套 Value 归配置所有；测试注册完成后再触发另一次 save。

### A02 / P0 / 确认：畸形签名长度走不安全窄化

- `src/api.zig:414-416` 解码外部签名后调用 `ctEqual`；`:1434-1438` 长度不等时把 usize XOR 直接 `@intCast` 为 u8。
- 对某些较长签名长度，值大于 255；安全构建发生 panic，small 构建也不能把它视为安全拒绝路径。
- 未发攻击性请求、未验证公网可利用性。
- 建议：先检查 HMAC 签名长度恰为 32，再常量时间比较；长度不匹配返回 false，不做可溢出窄化。

### A03 / P1 / 确认：改密码没有撤销旧管理员令牌

- `src/api.zig:410-421` 仅校验 HMAC 和 exp，忽略 payload 用户；`:866-877` 改用户名/口令不改变会话版本或签名密钥。
- Go `server/middlewares/auth.go:55-68` 查用户、校验 PwdTS 与禁用状态。
- 后果：旧凭据泄露时，“改密码”不能让已签发 token 立即失效。
- 建议：单管理员也保留 password/session version，令牌绑定用户名和版本，改密后原 token 返回 401。

### A04 / P1 / 确认：下载 sign 和 JWT 兼容承诺不成立

- Zig `src/api.zig:382-385` 生成两段 `payload.signature`，Go `server/common/auth.go:23-33` 生成标准三段 HS256 JWT。
- Zig `checkAuth():396-421` 接受 Authorization/token，却完全不验证 `sign`；与 `:220-221`“下载也接受 per-file sign”的注释矛盾。
- Go `pkg/sign/hmac.go:17-45` 的签名绑定路径和到期时间；Zig Obj.sign 常常只是驱动 id/路径，不能当权限签名。
- 后果：需要 per-file sign 的浏览器下载/播放链无法直接复用；不能把私有两段 token 称为标准 JWT。
- 建议：要么补标准 token 和文件签名接口，要么明确新认证协议并调整前端；没有签名验证前不要放行 sign 请求。

### A05 / P1 / 确认：fs/get 丢失代理与调用者头部语义

- `src/api.zig:505-509` 直接以空 LinkArgs 取链，并把 `lk.url` 当 raw_url 返回；Local 的 lk.url 本来为空，quark/itvsh/WebDAV 的代理要求与必要头都没体现。
- `/d/`/`/p/` `:1073`、WebDAV `src/webdav.zig:224` 也没有将 req.headers 传给驱动。
- Go `server/handles/fsread.go:318-339` 必须代理时构造本站 `/p/...`，非代理取链携带客户端头。
- 后果：Local raw_url 为空；必须带 Cookie 的盘可能把不可直用的 CDN URL交给前端；115即使修 downUrl，主应用仍未透传 UA。
- 建议：统一 link 参数传递；raw_url 对 proxy/local 返回可鉴权的本站 URL，再验证浏览器/播放器实际链路。

### A06 / P1 / 确认：文件类型编号与 Go 完全不同

- Go `internal/conf/const.go:171-178`：UNKNOWN=0、FOLDER=1、VIDEO=2、AUDIO=3、TEXT=4、IMAGE=5；`pkg/utils/file.go:142-163` 按扩展名决定类型。
- Zig `src/model.zig:7-11,40-41`：file=1、folder=2；`src/api.zig:486,523-524,1268` 将这套值输出给前端。
- 后果：文件可能被识别成目录，目录可能被识别成视频；即使 is_dir 正确，基于 type 的图标/预览分支仍不兼容。
- 建议：复用 Go 的 API 枚举，并测目录、mp4、mp3、txt、png、未知扩展名。

### A07 / P2 / 确认：根挂载、嵌套挂载与前端分页未完整兼容

- `src/api.zig:454-455` 请求 `/` 总走 listRoot，不调用实际 `/` 根驱动；`:481-489` 将每条 mount_path 去斜杠作为名称，嵌套 `/nas/photos` 展示为单个含斜杠的名字，没有虚拟中间层。
- `/api/fs/list` 没消费 page/per_page；Go `server/handles/fsread.go:109,214-225` 返回请求页和总体数量。
- 建议：定义虚拟挂载树与根驱动合并策略；分页在 API 层执行，避免前端分页重复显示整目录。

### A08 / P1 / 确认：配置/App 变更缺少并发保护

- `src/http.zig:414-419` 每个连接独立线程；注册 `src/api.zig:333-350` 是无锁“检查 → 写入”；设置 `:824-895` 与持久化 `src/main.zig:215-223` 同时修改配置 arena/JSON/固定 `.tmp` 文件。
- Cookie jar 本身有锁（`src/cookiejar.zig:71-87`），不等于整个配置保存链或管理员字段有锁。
- 后果：并发首次注册可都通过；并发保存可能冲突，长期 arena 也被不同线程修改。
- 建议：对配置读改写与初始注册做事务/互斥；写盘失败回滚或明确内存未提交。

## 5. 内存、I/O 与 HTTP 公共层

### M01 / P0 / 确认：分块云上传实际上累积整文件内存

- Source.readAll（`src/model.zig:151-159`）新分配 data；多个循环使用同一个 request arena，无块级释放。
- `src/drivers/cloud189.zig:1013-1018` MD5 第一遍保存每块 buffer 到请求生命周期；`:1053-1055` 正常上传第二遍又分配一遍。
- 同类：`aliyundrive.zig:1164-1178`、`quark.zig:839-843`、`123open.zig:983-991`（还拼 multipart）、`cloud189pc.zig:1917-1925,1967,2006`。
- Go 阿里 `drivers/aliyundrive_open/upload.go:241-253` 每块 GetSectionReader 后 FreeSectionReader；Go189 `drivers/189/util.go:398-407` 使用逐片短生命周期 buffer，另有 Go GC。
- 后果：HTTP spool 已落盘也救不了；这些云上传的 RAM 成本仍可能随整文件增长，189两遍甚至保留近两份 payload。不能称为恒定内存分块流式上传。
- 建议：块级临时 arena/可复用 buffer；哈希用固定 buffer 流读；每个并发 worker 明确内存预算；用大文件实测 RSS 峰值。

### M02 / P1 / 确认：客户端无限缓冲，并把截断响应当成功返回

- `src/client.zig:347-357` 将完整响应 append 到 Buf，无 body cap；`:285-294` 读取错误只记 debug，仍返回原 status + 残缺 body。
- 远程 Range 未命中时先缓存完整文件：`src/api.zig:1131-1171`。该缓冲限制先前已有记录，但“读取失败仍成功”是独立问题。
- WebDAV COPY 连本地源都全量读内存：`src/webdav.zig:441-459`；远端再 dupe 一份。
- 建议：分开小 JSON 限长读取与大文件 streaming；传播读取错误/校验期望长度；COPY 用可随机读 Source，别整体 materialize。

### M03 / P1 / 确认：前端静态资源请求消耗长期 arena

- `src/frontend.zig:151-171` 每次公开 asset 请求都向 `self.arena` 分配拼接 URL/文件路径，到进程结束才释放；并发请求还共用此 arena。
- 建议：asset 接受 request allocator，或者返回稳定路径分量给请求层拼接；测连续请求与并发后的内存趋势。

### M04 / P1 / 确认：配置失败路径与反复保存内存管理不足

- `src/config.zig:208-229` 创建 Config/arena 后没有 errdefer；读文件、写默认值、parse失败等会漏对象与分配。
- 之前磁盘满触发的是实际 I/O 失败；“NoSpaceLeft 导致无法运行正常测试”与“失败清理确有泄漏”同时成立，不能统称假泄漏。
- `save():147-153` 每次 stringify 和 tmp path 都分配到长期 arena；`syncStorages():168-190` 持续重建数组，还吞 OOM 错误。
- 建议：补错误释放，用短生命周期 scratch 做序列化，配置表更新可回收；错误不静默报告成功。

### N01 / P1 / 确认：client 超时/CA/跳过证书校验配置没有生效

- `src/client.zig:98-107` 宣告 timeout_s/insecure_skip_verify/ca_bundle_path；init/send 的实现未消费这些字段，仅使用 user_agent。
- `src/config.zig:246,253-254` 虽解析对应配置，业务工厂通常以 `.{} `构造 client。
- `src/client.zig:215-216` 锁覆盖整个请求；一条长时间等待的上游请求会阻塞共享 client 上的后续调用。
- Go `internal/net/serve.go:286-290` 明确将 TLS 配置应用到 transport。
- 建议：实际接入 deadline、可控 CA bundle，并沿 driver/main 传递选项；不要假称 Zig 自带当前项目必需的全部 roots。设备证书文件是否存在需另测。

### N02 / P1 / 确认：代理回源不跟随 3xx

- `src/client.zig:62,64` 默认 false/5；`src/api.zig:1143-1151` 与 `src/webdav.zig:255-265` 没开 follow_redirects，3xx 被改为 502。
- Go `internal/net/serve.go:275-280` 允许最多10次，移除 Referer。
- 建议：**仅在代理/普通回源显式跟随**，保留天翼/itvsh那些把302当业务状态的调用点；不可盲目全局改默认值。

### N03 / P1 / 确认：手写重定向对非默认端口/网络路径引用不正确

- `src/client.zig:363-373` 拼相对 Location 时只用 b.host，丢弃原端口；`//cdn.example/x` 也进入“原 host + 路径”分支。
- 已显式启用 redirects 的登录/CDN链可能受影响；具体上游出现这种 Location 尚未联网验证。
- 建议：实现 RFC URI resolution，保留 authority/port，正确处理 scheme-relative、query-only、dot-segments。

### N04 / P2 / 风险：Content-Encoding 没有解压

- `src/client.zig:349` 使用 resp.reader。Zig0.17标准库 `lib/std/http/Client.zig:722-736` 明确这个接口返回压缩字节，解压需 `readerDecompressing():748`。
- 默认请求 identity，因此**不能说所有 JSON 都失败**；但阿里/夸克分片显式发 gzip，其他上游也可能返回压缩体。
- 代理又未完整透传 Content-Encoding，客户端拿到的可能是未标注压缩的正文。

### H01 / P1 / 确认：HEAD响应长度冲突且可能发送正文

### H02 / P0 / 确认 + 条件风险：请求体定界验证不严

### H04 / P1 / 确认：连接/并发上限是未使用配置

### J01 / P1 / 确认：JSON浮点转整型不做范围校验
